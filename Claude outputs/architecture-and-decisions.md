# Music Library Organizer — architecture & decisions

_Started 2026-09-01. This mirrors `docs/decisions.md` and `docs/architecture.md` in the repo — update both when things change. The full long-term phase-by-phase plan (deliverables + required testing per phase) lives in `docs/roadmap.md` in the repo — this doc stays high-level._

## The problem

New music lands in an inbox folder, then gets manually sorted into subcrates in Serato. That sorting only exists inside Serato's crate database — decoupled from where files physically sit (confirmed against the real library) — so there's no single, portable folder structure Rekordbox (or anything else) can be pointed at. Serato ends up as the accidental source of truth.

## v0 scope

Read the current Serato crate organization and copy files from wherever they live into a new folder tree that mirrors it, under a target root that isn't owned by either DJ tool. One crate = one folder, always — a track in multiple crates gets copied into all of them, no exceptions. Copy first; move is an explicit, opt-in follow-up.

## End-state architecture (decided 2026-09-02)

James's mental model, confirmed: the canonical tree becomes the real source of truth, with two distinct things it produces:

1. **A local library on James's PC** — the canonical folder tree itself. This is what v0 already builds (copy-only, non-destructive).
2. **"Burn to flash"** — an export that takes the canonical tree and writes a real `_Serato_` folder (audio files + a freshly-generated crate database) onto a target volume, so *any* Serato install on *any* machine sees the full crate structure the moment that drive is plugged in. This is functionally what Rekordbox already does natively with its own USB export feature — Serato has no first-party equivalent, which is a big part of why this tool (or Lexicon) has value at all.

**Two different "write Serato" operations, kept deliberately separate** — this library represents 5 years of James's work, so risk is being managed explicitly, not just "be careful":

- *Writing a fresh crate database onto a new/scratch volume* (burn to flash) is comparatively low-risk — it never touches anything James currently relies on.
- *Pointing James's live, currently-in-use `_Serato_` database at the canonical tree* (so day-to-day sorting happens against the canonical folder going forward) is a much later, much higher-risk step, since it means writing into the one database Serato actually uses right now.

**Sequencing, each gated on the previous step being solid** — now formalized as roadmap phases (see `docs/roadmap.md`):

1. **Phase 1**: ship a trustworthy v1 — real installer, full run on real hardware/data, progress reporting for large scans, first e2e tests.
2. **Phase 2**: build a **crate writer** — the inverse of the already-validated crate reader. Software side is fully done (writer + hand-picked round-trip suite + property-based round-trip suite + a path-safety audit, see decisions 13, 15, 16 below), and its manual hardware checkpoint has now happened for real (decision 24) — see Phase 3 below for what it actually found.
3. **Phase 3**: "burn to flash," with incremental diffing (content-hash track identity) so re-burning a 5-year library isn't a full re-copy every time. Design decided in decision 17; the software stack (`TrackIndexStore`, the diff engine, the burn orchestrator, and the desktop UI flow) was built and verified by James's own `npm run typecheck`/`npm test` run (decisions 18–20) — but the real hardware checkpoint (decision 24) found that a `.crate`-only burn is genuinely incomplete: Serato's UI never shows any of it, because `.crate` files are filtered *views* into Serato's separate master index (`database V2`), and a track that index has never heard of doesn't render as found. That gap is being closed as its own phase — **Phase 3b**, see below — rather than folded into Phase 3 or Phase 4, since it's neither "more burn-to-flash software" (already built and correct) nor "edit James's live database" (Phase 4's much higher-risk territory).
4. **Phase 3b** (new, 2026-09-11): a **`database V2` writer**, so a freshly burned drive shows up in Serato with no manual "add this folder" step — the thing that actually finishes Phase 3's original promise. Explicitly scoped to *creating* a `database V2` from nothing on a blank drive that never had one, never *editing* an existing one — that stays Phase 4's much higher-risk territory. The format itself is fully understood (decision 25): same chunk framing as `.crate` files, confirmed by parsing James's real 11,991-track `database V2` byte-by-byte rather than trusting a write-up. As of decision 26 (2026-09-12), the writer itself and its `burnToFlash.ts` wiring are also done and tested. As of decision 27 (2026-09-14), the hardware trust gate itself passed — a blank-drive burn shows up in Serato correctly with no manual step — and that same hardware test's re-analysis regression is diagnosed and fixed. **As of decision 28 (2026-09-14), the phase's remaining open question is resolved and the desktop UI is wired end-to-end**: a real burn from the app now defaults to reading already-analyzed records from James's library backup (never his live `E:\_Serato_\database V2`), shown read-only on the "Burn to flash" card, with the burn report surfacing how many tracks were preserved from prior analysis. Only the actual hardware validation burn using this UI is still ahead.**
5. **Phase 4**: only after phases 2–3b are trustworthy, an explicitly opt-in flow to point James's actual live Serato setup at the canonical tree — mandatory full backup first, rollback path tested before it's ever needed for real.
6. **Phase 5**: Rekordbox side. Research (2026-09-08, against a real flash-drive export James provided) found the picture is better than the original "likely encrypted, likely hard" caution: the classic USB/CDJ export format (`export.pdb`/`exportExt.pdb`) is unencrypted and tractable — only the modern `exportLibrary.db` format is genuinely encrypted and stays out of scope. The read side is now fully done: both the flat-track reader (2026-09-08) and the playlist/crate-hierarchy reader (2026-09-10, decision 21) are built, tested, and validated against real Rekordbox/CDJ hardware exports — and, as of decision 23, independently cross-checked against a second, unaffiliated parser with an exact match. The write side (task #22) is the only piece left for this phase.
7. **Phase 6**: library management features beyond porting — audio tag reading/writing, duplicate detection, an in-app library browser, conflict resolution UI, backup/versioning for the canonical tree itself, move mode.
8. **Phase 7**: polish and sharing — signed installer, real first-run experience, CI/e2e expansion, and (since this doubles as a QA/SDET portfolio piece) a written test-strategy doc and eventual case-study write-up.

The **track-identity strategy** question (filename vs. content hash vs. tags) is now resolved: content hash, added as a new concept alongside the existing path-based `id` rather than replacing it — see decision 17.

## Decisions made so far (chronological)

1. **Stack**: Node/TypeScript across the board — reuses James's Playwright/Jest/Cypress testing experience directly, since this doubles as a QA/SDET portfolio piece.
2. **Packaging**: local-first, ultimately Electron (not a hosted service) — the tool only touches James's own files, and Serato/rekordbox/Lexicon are themselves desktop apps. Sequenced as "validate the Serato-reading logic first, repackage after."
3. **Crate-database reader validated** against the real `_Serato_` folder (`E:\_Serato_`, flash drive) — format assumptions matched real `.crate` files exactly; fixed `volumeRoot` semantics (parent of `_Serato_`, confirmed `E:\`).
4. **Multi-crate membership resolved**: one crate = one folder, always — James's call, no classification. Needed zero code changes; proven with a dedicated test.
5. **Electron pivot, now built**: `packages/server` (Express) and `packages/web` (standalone React) retired in favor of one `packages/desktop` package (`src/main`, `src/preload`, `src/renderer`), following `electron-vite`'s convention — reasoning: renderer and main process always ship together as one installer in Electron, so splitting them into separate packages doesn't match how the app actually deploys (same logic that ruled out a separate repo for backend work — see below). IPC (`contextBridge` + `ipcMain.handle`/`ipcRenderer.invoke`) was chosen over keeping an HTTP server running inside Electron, specifically because it's the idiomatic, more secure Electron pattern and James wants to learn it, not just the fastest path to something running.
6. **Design system adopted from James's portfolio site** (`_Portfolio/portfolio`): CSS custom-property tokens (colors via `light-dark()`, a three-radius rule, a one-accent-color rule), CSS Modules + atomic-design component structure (atoms/molecules). Deliberate divergence: system fonts instead of the portfolio's licensed `TBJ-Orcherum` font, since that font requires a private-repo token to build — not appropriate for an app shared with friends. Documented in `docs/design-system.md`.
7. **Per-action loading states**: `App.tsx` tracks *which* action (scan/plan/dry-run/execute) is in flight, not just a single boolean, so each button shows its own state (e.g. "Scanning…") while the others go inert — since the actions are sequential and share state, all four still disable together while any one runs.
8. **Long-term roadmap written** (`docs/roadmap.md`): phases from v0 through Rekordbox support and portfolio polish, each with concrete deliverables and the specific testing (unit/integration/e2e/manual/data-safety) required before the next phase is trusted. Ordered by risk, not feature value — nothing that writes to real Serato data ships before the phase before it has a passing, repeated round-trip test suite.
9. **Real scan progress reporting**: `invoke`/`handle` alone can't stream, so main pushes `ScanProgress` events (`event.sender.send`) as it walks a folder tree or reads crate files, and the renderer subscribes (`onScanProgress`) and renders a real `ProgressBar` atom. Determinate (a real %) only when a total is knowable upfront — crate-database scans know the file count before starting; folder-tree scans don't, so they stay indeterminate (a running count only) rather than faking precision.
10. **Selective-copy toggle tree**: since the tool does full writes, James asked for control over what gets copied, not just all-or-nothing. A checkbox tree (`SelectionTree`) over the scanned crates/folders — unchecking a node excludes its whole subtree; no independent carve-out of a child under an excluded parent (kept deliberately simple). The actual filtering (`filterTreeBySelection`) is a pure, tested `core` function; the IPC contract carries plain `excludedKeys: string[]`; `planOrganize` filters before planning. Nodes default to selected, so this is purely additive to existing behavior.
11. **Rekordbox research + a real read-only reader**: validated the classic `export.pdb`/`exportExt.pdb` USB-export format byte-for-byte against a real flash-drive export James provided — unencrypted, page-chained tables, row-group indexing, cross-referenced against Deep Symmetry's djl-analysis docs. `exportLibrary.db` (the modern format) is confirmed encrypted and stays out of scope. The validated prototype is now real code: `packages/core/src/rekordbox/pdbReader.ts`, same async-wrapper/pure-parser shape as the Serato readers, with a 6-test synthetic-buffer suite (no real personal library data committed to the repo) — all passing. Reads flat track rows (id/path/filename/title) only so far; playlist/crate hierarchy isn't read yet, and it isn't wired into desktop IPC/UI yet. Write-side strategy (template-modify a real export vs. rekordbox XML) is a separate open decision — see `docs/roadmap.md` Phase 5 and task #22.
12. **First Playwright `_electron` e2e test written**: `packages/desktop/e2e/scan-plan-execute.spec.ts` + `playwright.config.ts` — launches the real built app and drives scan → plan → dry run → execute through its actual UI, in folder-tree mode, against a small checked-in synthetic fixture (`e2e/fixtures/synthetic-library/`, never real library data), asserting on the real filesystem afterward. Native `dialog.showOpenDialog` is stubbed in the Electron main process per Playwright's documented pattern. **Structurally verified only, not yet run from this session**: this session's remote-device shell is a Linux VM but the project's `node_modules/electron` there is the Windows build, and a scratch Linux Electron install failed since its download needs `github.com`, outside that shell's network egress. James needs to run `npm run test:e2e` (or the new `npm run verify`, see decision 14) on his own machine for the first real pass/fail.
13. **Crate writer, round-trip proven (Phase 2's core deliverable)**: `packages/core/src/serato/crateDatabaseWriter.ts`, `writeCrateDatabase(tree, subcratesDir, { volumeRoot })` — the mirror of the reader, same chunk format/encoding/path convention exactly, since the two only mean anything as a matched pair. One `.crate` file per canonical-tree node with direct tracks (matching "one crate = one folder"); a purely organizational folder with only children and no tracks of its own gets no file. Round-trip test suite: write a hand-built tree → read it back with the trusted reader → deep-equal the shapes, covering nested crates, unicode in folder and file names, an empty intermediate folder, and one track shared across two crates. Committed.
14. **One `npm run verify` for everything**: `npm test` alone was confirmed to only run each workspace's Jest suite — never `build`, `typecheck`, or `test:e2e`. Added a `typecheck` script to `packages/core` (previously only `desktop` had one), root `typecheck`/`test:e2e` scripts that fan out to the workspaces, and a root `verify` = `build && typecheck && test && test:e2e`, so there's one command for "did I break anything" instead of remembering each check separately. `build`/`typecheck`/`test` were confirmed working through the new wiring; `test:e2e`'s Electron launch still needs James's own machine, same gap as decision 12.
15. **Property-based round-trip testing closes Phase 2's software side**: `__tests__/crateDatabaseWriter.property.test.ts` (`fast-check`) generates many random two-level tree shapes and round-trips each one — 40 + 25 random cases per run, all passing. It found something real on the first run: a node with no tracks *anywhere in its own subtree* writes no file at all and so doesn't survive a round trip — not a bug, since Serato's format has no file that could represent a wholly empty folder, but a real property worth knowing before Phase 3's incremental-diff logic gets built. Documented directly in `crateDatabaseWriter.ts`'s module doc.
16. **Path-traversal audit found and closed a real vulnerability in already-shipped code (not the new writer)**: asked to do one last edge-case pass for anything that could corrupt files or paths before moving on. `readCrateDatabase` builds tree segments by splitting a `.crate` FILENAME on `%%` with no validation of the result — a file literally named `..%%Evil.crate` parses into segments `["..", "Evil"]`. `planFromCanonicalTree` (shipping since Phase 0) then joined those segments into a target path with plain `path.join` and never checked the result stayed inside the chosen target root — so that one file could silently plan a copy *outside* it. `readFolderTree` can't produce this (real folder names from `fs.readdir` are never `..`), but nothing was stopping a corrupted or hostile `.crate` file from doing it. **Fix**: `planFromCanonicalTree` now verifies every computed target path is still under the resolved target root before adding it to the plan, and throws otherwise — proven end-to-end in `__tests__/planner.test.ts` by writing a real `..%%Evil.crate` file, reading it with the actual reader, and confirming the plan step refuses it. Applied the same class of hardening to `crateDatabaseWriter.ts` while it was fresh: its `%%`-guard now also rejects a path separator or a `.`/`..` segment, plus a new check against two different tree nodes colliding on the same `.crate` filename (would silently overwrite one with the other). Full `core` suite is now 44 tests, all green, clean typecheck both packages. Committed by James as "Additional edge cases."
17. **Phase 3 design decided: content-hash identity, an index cache, and additive-only diffing**: three connected design questions, settled before any Phase 3 code is written. (a) Content hash is a *new*, separate concept, not a redefinition of `TrackRef.id` (which stays path-derived and untouched everywhere it's already used) — and it's computed lazily by whatever diffing/burning code needs it, not eagerly by the existing readers, since a plain scan today does zero file-content reads and forcing every scan to hash every track's bytes would make ordinary scanning slower for no benefit outside this phase. (b) A new `TrackIndexStore` interface (`get`/`set`/`all`/`load`/`save`) is the only thing `core` code depends on for caching a computed hash across runs; the first implementation is a plain, atomically-written JSON file (path → size/mtime/hash), trusted only while size+mtime still match — the same cheap-stat-before-expensive-read trick git/rsync use. SQLite was deliberately not chosen for now: at personal-library scale (tens of thousands of tracks) JSON is fast enough, and a native module like `better-sqlite3` would be a new category of Electron packaging risk for a project with zero native deps today; the interface exists so a SQLite-backed implementation could slot in later (Phase 6's dedup/browser features) without touching planner/executor code. (c) Diffing against a destination is additive-only, never delete — a destination file with no matching source track is left alone (wasted space, never data loss), matching the project's whole "prove it before it's destructive" posture; an explicit, separately-designed cleanup step is future scope, not part of Phase 3. Concrete shape: `packages/core/src/trackIndex/` (the store), a diff step comparing the source tree against what `readFolderTree` finds at a destination (classifying each track new/unchanged/changed), and a burn-to-flash orchestrator that composes diff → plan → execute → `writeCrateDatabase` → a read-back verification pass — which is also where Phase 2's still-open manual hardware checkpoint finally gets exercised for real. Full write-up in `docs/decisions.md` and `docs/roadmap.md`'s Phase 3 section.
18. **Phase 3, first two deliverables built: `TrackIndexStore` and diff-driven copying**: `packages/core/src/trackIndex/trackIndexStore.ts` implements decision 17(b) — `JsonTrackIndexStore` (atomic writes via temp-file + rename, starts empty on a missing or corrupted file) and `hashWithCache(store, absolutePath)`, which stats a file first and only re-hashes its contents when size/mtime don't match the cache. Note this takes a plain absolute path rather than a `TrackRef`, a deliberate refactor from the first draft — the diff step below needs to hash destination-side files too, which aren't `TrackRef`s. 11 new tests, including one that deliberately seeds a wrong cached hash and confirms it's trusted when size/mtime match, proving the cache is actually consulted rather than silently bypassed. `packages/core/src/organizer/diff.ts` implements decision 17(c) — `diffAgainstDestination` classifies every source track against the destination as `new`/`unchanged`/`changed`; `planFromDiff` filters to only what needs writing; `summarizeDiff` gives the counts for a UI. Building the "changed" path surfaced a real, pre-existing gap in the executor: it only knew how to rename a colliding file aside (the accidental-collision case), with no way to say "no, overwrite this on purpose, I already diffed it." Fixed by adding `ExecuteOptions.allowOverwrite` and a new `'overwritten'` status, rather than papering over it in the diff code — 2 new executor tests plus the diff suite's own end-to-end cases ("burning twice copies nothing the second time," "a third pass after a source file changes re-copies only that file").
19. **Phase 3's burn-to-flash orchestrator, built and verified**: `packages/core/src/serato/burnToFlash.ts` — `burnToFlash(tree, volumeRoot, { store, mode })` composes decision 17(c)'s diff → `planFromDiff` → `executePlan({ allowOverwrite: true })` → a freshly regenerated crate database → a read-back verification pass, exactly as designed in decision 17. Caught a real bug before it ever ran against hardware: the first draft fed `writeCrateDatabase` only the tracks that got copied in a given run, which would have made every previously-burned but *unchanged* track silently vanish from the regenerated crate database on the second and later burns — the audio file untouched on disk, but Serato no longer able to find it in any crate. About as bad as this project's failure modes get, and it would only have shown up on a *second* burn, not the first. Fixed with `treeAtDestination(tree, diff)`, which remaps every track in the full diff (not just the filtered plan) to its destination path before the crate database is written, so every track — new, changed, or untouched — is represented every time. Proven directly in a dedicated test: burn once, add one new track, burn again, confirm the original track is still there. `verifyBurn` compares track-ID sets between what was intended and what a fresh read-back finds, not tree shape, sidestepping the empty-subtree round-trip quirk from decision 15. 6 new tests in `burnToFlash.test.ts` (first burn from empty, a no-op second burn, adding a track, overwriting a changed track in place rather than renaming it, confirming the source tree object itself is never mutated, nested crate hierarchies).
20. **Phase 3's UI flow wired up and verified (Phase 3's software side is now fully done)**: added a "Burn to flash" IPC round trip end to end — `diffBurn`/`burn` channels in `shared/ipcContract.ts`, plain testable handler functions in `main/ipcHandlers.ts` (4 new tests, covering preview-writes-nothing, a real burn, a no-op second burn, and `excludedKeys` respected the same way `planOrganize` already does it), the `ipcMain.handle` wiring in `main/registerIpc.ts`, the `contextBridge` exposure in `preload/index.ts`, and a new "Burn to flash" card in `renderer/src/App.tsx` (target-folder picker, preview/burn buttons, a diff-summary line, and a verification-gated success/warning block). The content-hash cache's file path (`app.getPath('userData')/track-index.json`) is computed once in `registerIpc.ts` and passed into the handlers as an explicit `storePath` parameter rather than read from a module-level singleton — keeps `ipcHandlers.ts` at zero Electron imports, same pattern `scanFolderTree`'s `onProgress` callback already used. Built while this session's connection to James's machine (`device_bash`) was down entirely, so every file went through a slower stage-and-commit fallback instead of editing in place — flagged plainly to James rather than silently claiming it was tested, since nothing had actually been typechecked or run from this session. James then ran `npm run typecheck` and `npm test` himself and confirmed everything passes ("All passing") — closing that gap. **Phase 3's full software stack (decisions 18–20) was verified this way — but decision 24 later found the phase's real-world goal wasn't actually met by this software alone.**
21. **Rekordbox reader extended to playlist/crate hierarchy, validated against real hardware**: Phase 5's remaining "read side" gap (flagged in decision 11) — `pdbReader.ts` read individual tracks but not how Rekordbox actually organizes them. Validated this time against a *second* real export, and a better one: a flash drive James connected that had actually been burned for and used on real CDJ/Rekordbox hardware (not just exported from the desktop app) — 3,549 tracks, 431 playlist/folder nodes, 4,037 track-in-playlist entries, every decoded name real and readable in a sensible hierarchy. Two new tables, same page/row mechanics as the tracks table: `playlist_tree` (a genuine parent-pointer hierarchy — unlike Serato's crates, which fake nesting via `%%`-filenames with no real parent links) and `playlist_entries` (flat `entryIndex`/`trackId`/`playlistId` rows). The page/row-walking loop, previously inlined just for tracks, was refactored into a shared `walkTableRows` helper so all three tables address pages/rows through the same already-proven logic. **A real format quirk, handled deliberately**: Rekordbox's data model can't attach a track directly to a folder, so its UI fakes it with a hidden child playlist literally named `_FolderTracks` under any folder holding direct tracks — confirmed on the real export. The new `packages/core/src/rekordbox/canonicalTree.ts` (`buildCanonicalTreeFromPlaylists`, the Rekordbox counterpart to `serato/crateDatabaseReader.ts`) folds those tracks into the parent folder and drops the node, rather than exposing Rekordbox's internal implementation detail as a visible subfolder — a genuine judgment call, flagged here and in `docs/decisions.md` in case a differently-shaped export ever disagrees with it. `playlist_entries` rows carry no validity marker (unlike track rows or playlist_tree rows), so a bogus entry is caught one layer up instead — `buildCanonicalTreeFromPlaylists` drops any entry whose track or playlist id doesn't actually exist in this export and counts it (`orphanedEntryCount`; 0 on the real export used to validate this). **Verified two ways, not just unit-tested**: alongside 12 new synthetic/plain-data tests (`pdbReader.test.ts` +5, new `canonicalTree.test.ts` +7 — the latter operates on typed arrays directly, since its job is reshaping already-parsed data, not decoding the binary format), the actual compiled reader was run against the real 3,549-track export in this session: 0 orphaned entries, all 4,037 entries placed in the tree, 0 `_FolderTracks` nodes leaking through as visible subfolders. `core`'s full suite — 82 tests, up from 70 — was run in full in a scratch checkout during this session, all green, clean typecheck, so this one is verified beyond the usual "James runs it on his machine" step, on top of that step still happening normally. Not yet wired into desktop IPC/UI — core-only, same pattern established since decision 11. Write-side strategy (task #22) is still open and untouched by this work.
22. **Burn verification strengthened after James asked a genuinely good question**: he has no CDJ/Rekordbox hardware to test against, has been burned before by a burn that "looked perfect" until a folder turned out wrong at a real gig, and asked whether that's even validatable without hardware. Two things are both true here. First, an honest ceiling: `verifyBurn` can only prove this project's writer and reader agree with each other — never that real Serato/hardware agrees too; only an independent oracle (a different parser, or the real app) can prove that, and no amount of re-reading our own output changes it. Second, and more actionable: re-reading `verifyBurn` while answering found it *was* weaker than it should have been even within that ceiling — it compared track ids as a flat, library-wide set ("does this track exist *somewhere*"), which cannot tell a track apart from that same track silently reassigned to the *wrong* crate. That's exactly James's failure mode, and the check as it stood would have reported `ok: true` on it. **Fixed**: extracted a new pure, exported `diffTrackPlacement(expected, actual)` that compares per-crate-path instead, and added `misplacedTrackIds` to `BurnVerification` (`ok` now requires it empty too) — 5 new tests including the exact swapped-crates scenario, proving it's caught rather than the missing/unexpected counts silently cancelling out. Also updated the desktop UI's verification message, which would otherwise have shown all-zero counts while still reporting failure. `core` suite: 87 tests (up from 82), clean. Discussed further options with James, not yet built: pointing Rekordbox/Serato's own desktop software (if available) at a burned volume as a cheaper oracle than physical hardware; cross-validating against an independent parser like `pyrekordbox`; and, for Rekordbox's still-open write-side decision (task #22), favoring template-modifying a real export specifically because it leaves nearly all of an already-hardware-proven file untouched. Full write-up in `docs/decisions.md`.
23. **Independent-oracle cross-check of the Rekordbox reader, requested directly by James: exact match, plus a corrected row-count safety finding**. He asked to check the project's Rekordbox process against `pyrekordbox` and `davehenke/rekordbox-mcp` — decision 22's "independent oracle" idea, actually acted on. Two candidates ruled out on inspection, correcting my own earlier assumptions: `pyrekordbox` only supports the newer `exportLibrary.db` SQLite format (OPUS-QUAD/OMNIS-DUO/XDJ-AZ hardware), not the classic `export.pdb`/`exportExt.pdb` format this project reads, at all; `davehenke/rekordbox-mcp` wraps `pyrekordbox` against Rekordbox's own live encrypted `master.db`, a different problem (live app database, not a USB export) and not comparable. The real find was `fragmede/rekordbox-pdb` (Python, MIT, dependency-free, independently written and documented, cross-checked by its own author against Deep Symmetry's Kaitai/crate-digger spec) — a genuine independent oracle for the exact format in scope. Ran it against the same real 3,549-track/431-node/4,037-entry hardware-burned export used to validate decision 21, built a from-scratch Python reimplementation of `buildCanonicalTreeFromPlaylists`'s fold logic on its output, and diffed against the TypeScript implementation's own output on the same file. **Result: exact match — 393/393 canonical nodes (392 real + synthetic root), 0 nodes only on one side, 0 mismatched paths.** Table layout, table type numbers, and both new row layouts (`playlist_tree`, `playlist_entries`) match FORMAT.md byte-for-byte. New fact worth carrying into the write-side decision (task #22): playlist ids are not stable across re-exports — Rekordbox reassigns them — which further favors the template-modify approach already leaning that way. **Also specifically checked for a named bug class**: FORMAT.md documents that the widely-used "`num_rows_large` (@0x22) if larger and ≠ 0x1fff" row-count heuristic — used by crate-digger and, per FORMAT.md's own note, by earlier versions of this project — silently drops rows on any page that ever exceeded 255 slots (a cited real example loses 78 entries this way). This project's current `readRowOffsets` does not read @0x22 at all; it reads `u8@0x18` combined with the low bits of `u16@0x19`, masked to 13 bits, which is algebraically the same function as FORMAT.md's stated-correct formula on every real page (the extra bits our mask admits beyond bit 0 of the `0x19` byte are structurally always zero there). Corroborated empirically, not just algebraically: `playlist_entries` rows are 12 bytes, so real pages comfortably exceed 255 slots, and all 4,037 real entries round-tripped with zero mismatches. **No code change required — this project's row-count decoding was already correct and not vulnerable to this bug class**; the finding is recorded so the reasoning doesn't need to be redone later. Separately, while investigating the CI failure this cross-check's own summary surfaced, found and fixed a real, small bug of my own making: widening `SeratoSourceType` in decision 21 to add `'rekordbox-playlists'` broke the desktop package's build, because `packages/desktop/src/shared/ipcContract.ts` had a hand-duplicated copy of that union instead of importing it — exactly the drift that file's own re-export pattern exists to prevent. Fixed by importing `SeratoSourceType` from `@mlo/core` there instead of re-declaring it; verified with a clean `tsc` run against a real built `@mlo/core` in a scratch checkout, mirroring the exact compile step that failed in James's CI log. Full write-up in `docs/decisions.md`.

## The repo-structure question, answered

James asked whether backend work needs its own repo. No — in a typical web app, frontend/backend sometimes split repos because they *deploy independently* (different hosts, release cadence, teams). In Electron, main process and renderer never deploy independently — they're bundled into one installer, always in lockstep. Splitting them (by repo, or even by package) adds coordination cost for zero benefit. Applied one level down: this is also why `server`/`web` were merged into a single `desktop` package rather than kept as three siblings — same test (does this piece deploy or version on its own?), same answer. `core` stays a separate package because it genuinely could be reused independently later (a CLI, a hosted API, Rekordbox tooling) — that's the actual dividing line, not "different layer of the stack."

## Electron architecture, in brief

- **Process model**: main (real Node, filesystem access, one per app) and renderer (Chromium, the React UI, no Node access) can't call each other directly — they pass messages. `ipcMain.handle('channel', fn)` in main, `ipcRenderer.invoke('channel', args)` in renderer. Progress events use the other direction — `event.sender.send`/`ipcRenderer.on` — since `invoke`/`handle` is request/response only and can't stream.
- **Preload + contextBridge**: `contextIsolation: true` + `nodeIntegration: false` mean the renderer can't see Node or raw `ipcRenderer`. `src/preload/index.ts` exposes a whitelisted `window.mlo` object instead — the renderer can only call the specific functions explicitly attached there.
- **Shared IPC contract** (`src/shared/ipcContract.ts`): channel names + TypeScript types for every call, imported by both main and renderer, so a mismatch is a compile error on both sides rather than a runtime surprise. As of decision 23, every type in this file that also exists in `@mlo/core` is imported from there rather than hand-duplicated, specifically so a future widening (like decision 21's `SeratoSourceType` change) can't silently drift again. As of decision 28, `burn`-only args (`BurnExecuteArgs`) are kept separate from the `diffBurn`/`burn`-shared `BurnArgs`, for the same anti-drift reason applied to a field only one of the two channels actually uses.
- **Native folder picker** (`dialog.showOpenDialog`) replaces the old "type a path into a text box" UI — one of the main reasons for going desktop in the first place.
- **Tooling**: `electron-vite` for dev (Vite + HMR for renderer, watch/restart for main+preload, one config), `electron-builder` for packaging.
- **Fixed while porting**: the old Express `/organize/plan` re-scanned the root path and only ever used the folder-tree reader (crate-mode plans were silently impossible). `planOrganize` now takes the already-scanned tree instead, and now also accepts `excludedKeys` to filter it before planning.
- **Path safety**: both write paths -- the copy/move planner (`planFromCanonicalTree`) and the crate writer (`writeCrateDatabase`) -- now verify every computed output path stays inside the folder they were told to write into, and throw rather than write if it wouldn't. See decision 16.
- **Content-hash identity & diffing** (decision 17, built in decisions 18–20): a `TrackIndexStore` seam for caching hashes across runs, kept separate from `TrackRef` itself; diffing against a destination is additive-only; a `burnToFlash` orchestrator ties diff → plan → execute → crate write → verify together, exposed through IPC and a UI card.
- **Dependency-injected cache path** (decision 20): the `TrackIndexStore`'s backing file path is computed once in `registerIpc.ts` (Electron-aware) and threaded into the plain handler functions as a parameter — the same shape `onProgress` callbacks already use — so `ipcHandlers.ts` stays free of Electron imports and directly unit-testable. As of decision 28, the same pattern extends to `sourceDatabaseV2`: main resolves it (with the default-existence check) and hands the resolved value in, rather than `@mlo/core` knowing anything about a hardcoded backup path.
- **Rekordbox CanonicalTree** (decision 21): `rekordbox/canonicalTree.ts` joins the raw pdb tables into the same CanonicalTree shape the Serato readers produce, using Rekordbox's real parent-pointer hierarchy directly rather than a filename convention — not yet wired into IPC/UI.
- **`database V2` is a flat master index, not a tree** (decision 25): unlike the crate/Rekordbox readers, `databaseV2Reader.ts` returns a flat track list, not a `CanonicalTree` — `database V2` genuinely has no folder hierarchy of its own (crate structure lives entirely in the separate `.crate` files, confirmed). Resolving its `rawPath`s and wiring the reader into the organizer/burn flow is later Phase 3b work, not done yet.
- **Two read paths into `database V2`, on purpose** (decision 27): `databaseV2Reader.ts` now has both a named-field parser (the original, understood-fields-only view used everywhere else) and a raw, undecoded-record parser used only by the burn orchestrator's carry-forward feature — the latter exists specifically to preserve fields this project doesn't have names for, rather than only what's already been reverse-engineered.
- **Explicit input vs. convenience default, two different trust levels** (decision 28): an explicit `sourceDatabaseV2` from a caller is trusted completely and fails loudly if wrong; `DEFAULT_SOURCE_DATABASE_V2` is only ever applied after confirming it actually exists, so a missing convenience default degrades gracefully instead of failing a burn that never asked for it.
